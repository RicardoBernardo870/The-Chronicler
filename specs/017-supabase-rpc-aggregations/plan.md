# Implementation Plan: Supabase RPC Aggregations

**Branch**: `017-supabase-rpc-aggregations` | **Date**: 2026-04-30 | **Spec**: [spec.md](spec.md)

## Summary

Replace all heavy client-side data aggregation with four PostgreSQL RPC functions
callable via `supabase.rpc()`. The current approach fetches entire raw tables
(`progress_history`, `books`, `reading_progress`) to the browser and computes
aggregates in JavaScript composables — causing over-fetching, race conditions on
page navigation, and fragile sequential store dependencies. The new functions
push page-delta calculation (using `LAG()` window functions), streak computation,
velocity averaging, and join logic into the database. Frontend stores and
composables are updated to call one RPC each and cache the result via the
existing SWR primitive.

## Technical Context

**Language/Version**: TypeScript 6 (strict) + Vue 3.5 (Composition API, `<script setup>`)
**Primary Dependencies**: Pinia 3, Supabase JS v2, PrimeVue 4, Vue Router 4, VueUse
**Storage**: Supabase PostgreSQL (existing tables — no schema changes); in-memory Pinia refs + SWR cache
**Testing**: Manual browser verification + Supabase SQL editor smoke tests
**Target Platform**: PWA (web browser, mobile + desktop)
**Project Type**: Web application (SPA PWA)
**Performance Goals**: Library page completes initial data load in a single network request; profile stats payload < 1 KB
**Constraints**: No new tables; no edge functions; no external backend; existing SWR caching must be preserved; TypeScript strict (no `any`)
**Scale/Scope**: Single-user per session; up to ~100 books; up to ~10,000 progress_history rows

## Phase 0 Research Summary

All technical decisions resolved in `research.md`:

| ID | Decision |
|----|----------|
| D1 | `LANGUAGE sql` (not plpgsql) — no procedural branching needed |
| D2 | `LAG() OVER (PARTITION BY book_id)` for page deltas — O(n log n), prevents cross-book contamination |
| D3 | `SECURITY DEFINER` + explicit `p_user_id` parameter — reliable auth context in RPC calls |
| D4 | UTC day bucketing for streaks — avoids per-user timezone dependency with no schema change |
| D5 | Rolling 3-session velocity — matches existing `useLastSession` algorithm exactly |
| D6 | Update existing stores independently — minimises blast radius vs full store merge |
| D7 | Four new cache keys (`library`, `readingStats`, `lastSession`, `libraryBreakdown`) alongside existing keys |

## Phase 1 Design Summary

### SQL Functions (contracts/sql-functions.sql)

| Function | Returns | Replaces |
|---|---|---|
| `get_library_with_progress(p_user_id)` | `json` (array) | `booksStore.fetchLibrary()` + `progressStore.fetchProgress()` sequential pair |
| `get_reading_stats(p_user_id)` | `json` (object) | `useReadingProfile` JS aggregation |
| `get_last_session(p_user_id)` | `json` (object or null) | `useLastSession` entire composable |
| `get_library_breakdown(p_user_id)` | `json` (object) | `useLibraryBreakdown` computed |

### TypeScript Types (contracts/typescript-interfaces.md)

New interfaces added to `src/types/index.ts`:
`LibraryBookEntry`, `BookStatus`, `ReadingStats`, `LastSessionSummary`,
`LibraryBreakdown`, `GenreDistributionItem`

### Cache Architecture (data-model.md)

Four new `cacheKeys` entries. TTLs: `library` 60 s, `lastSession` 30 s,
`readingStats` / `libraryBreakdown` 120 s. Write operations in `booksStore`
and `progressStore` extended to invalidate new keys.

### Race Condition Fix

`ProfilePage.vue` mount sequence changes from sequential
(`await books → await Promise.all([progress, dna])`) to parallel
(`await Promise.all([libraryWithProgress, dna])`).
The sequential constraint existed only because `progressStore._fetcher` called
`booksStore.bookById()` — eliminated by the unified RPC.
