# Implementation Plan: Vue Codebase Modernization

**Branch**: `014-vue-modernization` | **Date**: 2026-04-25 | **Spec**: [spec.md](spec.md)

## Summary

A pure-refactor initiative that improves code quality across the Vue SPA without changing any user-facing behaviour. Four workstreams run in priority order: (1) component decomposition of the two largest page files (DashboardPage 1049 lines, BookDetailPage 611 lines) into focused child components; (2) replacement of custom HTML badge/chip/banner elements with PrimeVue equivalents; (3) migration of all manual date arithmetic to a `src/utils/date.ts` wrapper over `date-fns`; (4) extraction of duplicated utilities (`coverFallback`) and named computeds for complex inline template expressions. No schema changes, no new Supabase calls, no new user-visible features.

## Technical Context

**Language/Version**: TypeScript 6 (strict) + Vue 3.5 (Composition API, `<script setup>`)  
**Primary Dependencies**: Pinia 3, PrimeVue 4, Vue Router 4, Supabase JS v2, VueUse — **adding `date-fns` v4** (one permitted new dependency per FR-009)  
**Storage**: No changes — Supabase PostgreSQL, existing schema  
**Testing**: `npm test` (Vitest) + manual browser verification against quickstart.md scenarios  
**Target Platform**: PWA (iOS, Android, desktop) — mobile-first, 375px min-width  
**Project Type**: Web application (Vue SPA / PWA)  
**Performance Goals**: Bundle size must not regress (date-fns is tree-shaken; net addition ≈ 0 kB for selective imports)  
**Constraints**: Zero functional regressions; zero visual regressions; build must stay clean after every increment  
**Scale/Scope**: `src/` directory only — ~7 000 lines across 40 components; no backend/edge function changes

## Key Design Decisions

### Why `src/utils/date.ts` wrapper instead of direct `date-fns` imports

One canonical import path means that if `date-fns` is ever swapped, only the wrapper changes. It also enforces consistent bucket labels (e.g., "Just now" for < 2 min) which `date-fns` `formatDistanceToNow` doesn't produce natively.

### Why glass-surface cards are kept custom

PrimeVue `Card` uses design tokens (`--p-card-*`) that don't map to the iOS liquid-glass aesthetic without deep `::deep` overrides in every theme. The override cost exceeds the consistency benefit — glass-surface wrappers are already consistent via the shared `.glass-surface` CSS class in `main.css`.

### Why `useCache.ts` `Date.now()` calls are excluded from migration

These are performance-timing primitives (cache TTL arithmetic), not human-readable date formatting. Replacing them with `date-fns` functions would be gratuitous and would change timing semantics slightly (e.g., `differenceInMilliseconds` adds function-call overhead to a hot path).

### Refactoring increment order (risk → reward)

1. `date-fns` install + `src/utils/date.ts` — zero UI risk; pure module addition
2. `coverFallback` extraction — surgical 3-line change; 4 files patched
3. Composable date migration — logic-only; no template changes; easy to verify
4. Component date migration — small per-file changes; build check after each
5. PrimeVue chip/tag/message replacements — contained per-component
6. DashboardPage decomposition — largest; done after simpler work stabilises confidence
7. BookDetailPage decomposition — second largest
8. `BookCard`, `LoreChronoscopeCard`, `RecapStream` internal refactors — polish

### Prop communication boundary

All extracted components are "dumb" — they receive props and emit events. They do NOT call Pinia stores directly (except where the original code already called them in sub-components like `SessionStartButton`). This keeps parent pages as the single source of truth and makes extracted components independently testable.
