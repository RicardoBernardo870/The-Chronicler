# Development Workflow

Last updated: 2026-10-18

How features are built for The Chronicler (code name BookHero) today: web PWA, shared Supabase backend, and the native iOS app that follows.

---

## How work is done (D-02)

Features are **implemented directly with Claude Code** using **Opus 5.5**. Large or cross-cutting work — a Phase 0 work package, a feature that spans several domains, an iOS phase — runs in **ultracode** mode from a written kickoff brief. Small changes are done in a normal session.

| Item | Status |
|---|---|
| Spec Kit (`/speckit-*` commands, `.specify/`, `.claude/skills/speckit-*`) | **Not used.** Legacy tooling left in the repo; do not run it and do not add Spec Kit steps to plans or briefs |
| `specs/001-…` to `specs/034-…` | **Historical reference only.** Useful background; where a spec disagrees with the code or the catalog, the code and the [business-rules catalog](../business-rules/README.md) win. No new `specs/` folders |
| `CLAUDE.md`, `AGENTS.md` | Auto-generated by Spec Kit and partly stale: "npm test; npm run lint" (there is no lint script and the repo uses pnpm), the `specs/034-library-import/plan.md` pointer, VueUse `useColorMode` (theming is `useAppTheme`) (PLT-D39, PLT-D41) |
| iOS app | Separate repo `bookhero-ios`. Its `CLAUDE.md` is derived from [`docs/ios-foundation/ios-constitution.md`](../ios-foundation/ios-constitution.md) (no `.specify` constitution). Each iOS phase starts from an ultracode kickoff brief in [`docs/ios-phase-prompts.md`](../ios-phase-prompts.md) |

### Sources of truth, in order

1. **Code and the live backend** (the read-only snapshot `supabase/reference/live-baseline-2026-10-18.sql` until BC-03 repairs migrations).
2. **[Business-rules catalog](../business-rules/README.md)** — numbered rules with stable IDs, known defects, open decisions and the owner decisions log (D-01 … D-17). The cross-client contract (D-01).
3. **[Backend contract](../backend-contract.md)** — the live backend surface.
4. **[Backend consolidation plan](../backend-consolidation-plan.md)** — Phase 0 packages BC-01 … BC-15.
5. This wiki ([Features](Features.md) is an overview that links into the catalog).

## Common commands

```bash
pnpm install          # pnpm only — npm install fails in this repo
pnpm dev              # Vite dev server (service worker disabled)
pnpm test             # vitest run
pnpm test:watch       # vitest watch
pnpm build            # vue-tsc -b && vite build
pnpm preview          # serve dist/ (service worker active)
```

There is no `lint` script and no CI; `pnpm build` is the type check.

## Building a feature

1. **Find the rules.** Locate the domain file in the catalog and the rule IDs involved, plus that domain's Known defects (`<PREFIX>-Dnn`) and Open decisions (`<PREFIX>-Qnn`). Check the decisions log: an answered decision is binding.
2. **Check the backend direction.** If the area is moving server-side in Phase 0 (progress and sessions BC-04, completion effects BC-05, time zones BC-06, recaps BC-07, Insights BC-08, achievements BC-09, review BC-10, account BC-11), build against the target RPC or coordinate with that package instead of adding more client-only logic (D-06). Native clients stay thin.
3. **Read the existing code** — the store, composables, pages and edge function for the area ([Architecture](Architecture.md), [Project Structure](Project-Structure.md)).
4. **Write the brief** (ultracode for anything large; see the template below).
5. **Implement** with Claude Code. Keep domain logic in stores/composables, pure rules in `src/utils/`.
6. **Test**: unit tests named after the rule IDs they protect ([Testing](Testing.md)); for backend packages, the database and edge-function tests in the plan's acceptance criteria.
7. **Verify**: `pnpm test` and `pnpm build`; `pnpm preview` for service-worker, routing or offline changes; a PWA regression pass when the backend changed.
8. **Update the docs in the same PR**: catalog rules (new IDs, changed rules, a defect closed, "client-only" → "server-enforced"), [backend-contract.md](../backend-contract.md) and the live snapshot for backend changes, [Features](Features.md) and the relevant wiki pages, [Changelog](Changelog-Release-Notes.md).

### Kickoff brief template (ultracode)

```markdown
# <Feature or BC-nn> — kickoff brief

Goal: <one paragraph: user outcome or backend capability>
Decisions in force: <D-xx list>
Rules in scope: <rule IDs, e.g. SES-12, PLT-45, BE-19> · Defects fixed: <IDs> · Open decisions touched: <IDs + chosen answer>
Acceptance criteria: <testable statements, each citing rule IDs>
Constraints:
- Client-agnostic and backward compatible: the current PWA keeps working (D-05; expand → migrate → contract)
- Server clock and server-owned effects for core logic (D-06)
- Reader IANA time zone for every day/week/month/year boundary (D-07)
- pnpm; TypeScript strict; Vue `<script setup>`; arrow functions only
Files likely touched: <paths>
Verification: <commands, manual checks, SQL/advisor checks>
Docs to update: <catalog files, backend-contract sections, wiki pages>
```

## Code style

- TypeScript strict; Vue 3.5 Composition API with `<script setup>`.
- **Arrow functions only** — never the `function` keyword (known drift: `useOfflineSync.ts`, `stores/recaps.ts`, `App.vue` `handleSwMessage`, `recapService.ts` `streamRecap`, PLT-D42).
- Prefer existing PrimeVue components and local patterns; glass surfaces via `assets/styles/glass.css`.
- Row mapping (snake_case ↔ camelCase) in `src/types/index.ts`.
- Persistence and SWR keys in Pinia stores (`cacheKeys` in `useCache.ts`); UI workflow state in pages/components; pure rules in `src/utils/`.
- Module singletons for state that must outlive a component; remember they are not reset on sign-out.
- Copy says "The Chronicler"; identifiers and storage keys keep `bookhero` (D-03).
- Client time is device time: timestamps sent to the server are ISO-8601 UTC (`toISOString()`); RPC `YYYY-MM-DD` fields are floating calendar dates.

## Backend changes

Every backend change is **client-agnostic and backward compatible** (D-05): the PWA, the future iOS app and later Android share one project.

| Rule | Detail |
|---|---|
| Expand → migrate → contract | Add columns, RPCs and versioned edge modes first; move the clients; retire legacy paths only after legacy-write counters read zero for 14 days (plan P2) |
| Migrations | One new timestamped file per change, committed and applied as-is; no dashboard SQL; no `supabase db push` from the drifted folder until BC-03 ([Deployment › Database changes](Deployment.md#database-changes)) |
| RPC naming | `verb_noun` snake_case; camelCase JSON keys in responses |
| Identity | From `(select auth.uid())`. Existing `p_user_id` parameters stay for PWA compatibility but must equal the caller; new RPCs take no `p_user_id` |
| Privileges | SECURITY DEFINER with pinned `search_path`; `revoke all … from public, anon`; `grant execute … to authenticated`; helpers in a non-exposed `private` schema |
| Errors | Business errors `raise exception '<code>' using errcode = 'P0001'`; authorization `errcode = '42501'` |
| Signature changes | `DROP FUNCTION` + `CREATE FUNCTION` in one migration with grants re-applied; never leave two overloads (`PGRST203`); new parameters last with defaults |
| Time zones | New RPCs take `p_timezone text default null` (parameter → stored reader zone → `'UTC'`); `get_book_passport_stats` keeps `p_time_zone` |
| RLS | Every new user-owned table: owner policies for every command, plus a book-ownership check when it has `book_id`; indexes for FKs and time-ordered queries |
| Docs | Update [backend-contract.md](../backend-contract.md), the catalog rules and the live snapshot in the same PR |

Full conventions: [plan §1.3](../backend-consolidation-plan.md#13-conventions-for-every-new-or-changed-backend-surface).

### Edge-function changes

1. Edit under `supabase/functions/<name>`. For `generate-lore` and `generate-reading-dna`, first sync the repo to the deployed (canonical) source (D-09; [Deployment › Edge functions](Deployment.md#edge-functions)).
2. Verify the JWT for real (signature and expiry; BC-02's shared `requireUser`), never trust a decoded `sub`.
3. Keep provider keys in secrets; never return internal error text.
4. New behaviour goes behind `apiVersion: 2` in the request body; requests without it keep the legacy contract until the PWA migrates.
5. Pin `npm:` imports; deploy with the correct `verify_jwt` flag.
6. Update [backend contract §10](../backend-contract.md#10-edge-functions) when a request or response contract changes.

## Debugging tips

- Console first: missing env variables, Supabase errors, unhandled rejections.
- Network tab: edge-function status codes and JSON `{ error }` bodies; 401s on `/rest/v1/` (the retry wrapper retries once).
- Dev builds: `window.__bookheroCache.keys()` / `.get(key)` / `.stats()` to inspect SWR freshness.
- Application tab: IndexedDB `chronicler-offline` → `progress_queue`; localStorage keys ([Configuration › Browser storage keys](Configuration.md#browser-storage-keys)); service-worker state.
- Service-worker issues: test with `pnpm build && pnpm preview` in a fresh profile, or clear site data.
- Backend: Supabase function logs; security and performance advisors; read-only SQL (`pg_get_functiondef`, `pg_policies`, `has_function_privilege`) against the live project or the snapshot file.
- More: [Troubleshooting](Troubleshooting.md).

## Pull-request checklist

- [ ] Rule IDs in the PR description; catalog updated (rules, defects, decisions).
- [ ] `pnpm test` and `pnpm build` pass.
- [ ] Tests added or updated for changed rules.
- [ ] New environment variables or secrets documented by **name** in [Configuration](Configuration.md); no secret values anywhere.
- [ ] Backend: migration file, privileges, RLS, backward compatibility with the current PWA, [backend-contract.md](../backend-contract.md) and the live snapshot updated.
- [ ] Edge functions: real JWT verification, no internal error text, correct `verify_jwt` flag.
- [ ] User-facing behaviour reflected in [Features](Features.md) and the [Changelog](Changelog-Release-Notes.md).
